# VIRUS AI — протокол передачи задач между ChatGPT, Grok и Claude

## 1. Зачем это нужно

GitHub здесь — общий журнал и асинхронная почта команды, а не автоматическая шина между моделями. Каждый агент должен отдельно открыть репозиторий и читать/публиковать сообщения через свой доступ. Если у агента нет прав записи, он передаёт отчёт пользователю или координатору для публикации.

## 2. Роли по умолчанию

Роли — это ответственность, а не ограничение возможностей. Если один агент недоступен, координатор может назначить роль другому, явно записав замену.

### ChatGPT — координатор и интегратор
- Делит работу на небольшие проверяемые задачи и назначает владельца/рецензента.
- Проверяет контекст и существующие решения до выдачи задачи.
- Сводит результаты, разрешает противоречия через доказательства, ведёт журнал и определяет следующий шаг.
- Не объявляет тесты пройденными без фактического вывода.
- Не сливает PR и не включает реальные сделки автоматически.

### Grok — независимый исследователь и red-team
- Ищет альтернативные решения, свежие источники и потенциальные ошибки.
- Проверяет допущения, угрозы безопасности, граничные случаи и несогласованности архитектуры.
- Отмечает дату/версию источников и разделяет факты, гипотезы и мнения.
- Не дублирует работу интегратора без объяснения, зачем нужен независимый взгляд.

### Claude — инженерный исполнитель и ревьюер кода
- Предлагает конкретные изменения, тесты, рефакторинг и небольшие патчи.
- Проверяет совместимость с текущей архитектурой и регрессионные риски.
- При возможности выполняет тесты в доступной среде и прикладывает точные команды/вывод.
- Если не имеет доступа к исходникам или записи, не выдумывает результаты и запрашивает необходимые безопасные данные.

### Владелец проекта — утверждение риска и границ
- Решает вопросы доступа, публичности данных, крупных архитектурных изменений и релиза.
- Даёт отдельное явное разрешение на опасные/необратимые действия.
- Реальная торговля не активируется автоматически в рамках этих задач.

## 3. Жизненный цикл задачи

1. **INTAKE** — координатор создаёт задачу в Issue с ID вида `VAI-P0-001`, целью, владельцем и критериями приёмки.
2. **PLAN** — исполнитель отвечает планом: что изучит/изменит, какие файлы, риски, как проверит. Пока план не понятен, код не менять.
3. **EXECUTE** — исполнитель делает только согласованный объём. Существенное расширение задачи требует комментария.
4. **REPORT** — исполнитель публикует результат по шаблону ниже.
5. **REVIEW** — другой агент проверяет независимым взглядом: корректность, безопасность, регрессии, доказательства.
6. **VERIFY** — координатор сверяет критерии приёмки с реальными результатами. Статус `VERIFIED` разрешён только при наличии доказательств.
7. **HANDOFF** — в журнале фиксируются решение, commit/PR, остаточные риски и ровно следующий шаг.

Статусы: `PROPOSED`, `READY`, `IN PROGRESS`, `BLOCKED`, `REVIEW REQUIRED`, `UNVERIFIED`, `VERIFIED`, `REJECTED`. Не смешивать «код написан» с «код проверен».

## 4. Шаблон постановки задачи

Скопируй в новый GitHub Issue:

```markdown
## ID / название
VAI-Px-###

## Цель и причина
Какую проблему решаем и почему сейчас?

## Контекст
Ссылки на безопасные документы, коммиты, PR и прошлые решения.

## Владелец / независимый рецензент
Исполнитель: ChatGPT / Grok / Claude / человек
Рецензент: другой агент, не автор изменений

## Объём
Включено:
Не включено:

## Критерии приёмки
- [ ] Критерий 1 — проверяемый и конкретный
- [ ] Критерий 2 — проверяемый и конкретный

## Проверки
Команды, тестовые данные, ожидаемые результаты.

## Риски / ограничения
Безопасность, совместимость, приватность, откат.

## Статус
PROPOSED
```

```markdown
### Изменения

### Проверки
Для каждой проверки:
- Команда/метод:
- Среда/версия:
- Фактический вывод/exit code:
- Что этот результат подтверждает и чего не подтверждает:

### Невыполненное / риски
Явно указать пропуски, ограничения среды и неизвестное.
```


## 7. Правила разрешения разногласий

- Не голосовать за «самый уверенный» ответ. Сравнивать доказательства, воспроизводимость, источники и стоимость ошибки.
- Сначала сформулировать, в чём конкретно разногласие; затем запросить у каждого агента основания и способ проверки.
- Если данных недостаточно, итог — `INCONCLUSIVE` или `BLOCKED`, а не искусственный консенсус.
- Решение и оставшаяся неопределённость записываются в Issue.

## 8. Проверка результата

Уровни доказательств:
- **E0 — мнение/предложение:** нет проверки.
- **E1 — просмотр кода/документа:** указывается путь и конкретный участок.
- **E2 — локальная проверка:** команда, среда, exit code и существенный вывод.
- **E3 — CI:** ссылка на запуск, реально выполненные шаги и результат.
- **E4 — интеграционная проверка:** воспроизводимый smoke/integration test в целевой среде.

Нельзя повышать уровень доказательств без фактической проверки. Пустые логи, `runner_id=0` или job без шагов — это не E2/E3 и не доказательство прохождения тестов.

## 9. Приватность и безопасность

- Этот репозиторий публичный. Не добавлять приватный исходный код, секреты, API-ключи, токены, пароли, персональные данные или закрытые URL.
- Не просить агента публиковать секреты. Не вставлять токены в Issues, коммиты или логи.
- Если задача требует приватного кода, обсуждать только абстрактный план/безопасные фрагменты; реализацию выполнять в приватном репозитории с соответствующим доступом.
- Любой патч сначала проверяется, затем предлагается в PR. Не объединять автоматически.
- Для XAUUSD — только аналитика/сигналы, если владелец отдельно не утвердил иное; этот workflow сам по себе не разрешает реальные сделки.

## 10. Рабочая каденция
- Перед каждой задачей: прочитать журнал и последние комментарии.
- После существенного действия: оставить отчёт в том же Issue.
- При блокере: сообщить сразу, указать, чего не хватает, и предложить безопасный обходной путь.
- В конце сессии: обновить журнал одним коротким handoff-комментарием с текущим статусом и следующим владельцем.
